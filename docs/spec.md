# 学習アプリ（ai-quiz）仕様書

最終更新：2026-10-23（フェーズ1で決めたことを反映）

この仕様書は、アプリ全体の方針と決定事項をまとめたもの。原本は開発者が別に管理しており、変更があればこのファイルを差し替える。各フェーズの依頼文と食い違う場合は、依頼文を優先する。

## 目的

高校生の子供の勉強用に、ローカルLLMが作った問題のうち、検証を通ったものだけを出題するWebアプリ。試運転版はほとんど使っていないため、この仕様書をもとに作り直す。

- 対象：高校1年生〜大学生
- 問題は基本的にデスクトップPCのローカルLLM（Ollama、gemma4の12b・26b-QAT・E4Bクラスが上限）で作る。短い期間にたくさん作りたいときは、AnthropicのAPI（Claude）でも作れる（月の利用額に上限を設ける）
- 出題前にAIが一度解き、答えが合っているか・解けるかを確認する。数学の計算は必ずPythonで確認する
- 家庭内LANのどこからでも使える
- 過去の問題を見返し、再挑戦できる（正解・不正解・当時の回答を残す）
- 時事問題も出したい

### 利用者（子供）の要望

- スマホで使う
- 1日合計20問程度
- 選択式中心（数学も選択式でよい）
- 英語は共通テストレベル
- 公共を追加したい

## 構成

| 置き場所 | 動かすもの |
| --- | --- |
| NASのRaspberry Pi 4（4GB、arm64、常時稼働） | web（画面、ポート8000）、worker（作成依頼の処理・検証）、sandbox（Pythonでの検算）、データ（NASのHDD上） |
| デスクトップPC（Windows） | Ollamaのみ。IPはルーターで固定済み。電源が切れていることが多い |
| AnthropicのAPI（インターネット） | 問題の作成・検証・解説の見直しに使える。APIを使えばデスクトップPCなしでも作れる。APIキーはworkerだけに渡す |

- Pi 4ではOpenMediaVaultとOpen WebUIもDockerで稼働しているため、メモリに余裕がない
- 将来ミニPC（x86）へ移せるよう、arm64とx86の両方でビルドできるようにする
- OllamaのURLは環境変数で指定する
- APIの依頼とOllamaの依頼は別の順番待ちで、同時に進められる。APIの利用額には月の上限（初期値5ドル。/statusで変えられる）と1回の依頼の上限を設ける
- 子供の端末はスマホ。キーボード入力の問題はPC・ラズパイから解く

### 設計の原則

- 子供が操作する画面の処理では、LLMを一切呼ばない。LLMはworkerが作成依頼を処理するときだけ使う
- 検証を通った問題だけをストックに入れる
- デスクトップが停止していても、ストック問題を解く・過去問題の見返しと再挑戦・採点がすべてできる
- 科目を後から足しても中心部分を触らずに済む作りにする（科目ごとに生成・検証・採点を差し替えられる）

## 問題の作成と検証

- 作成は手動で依頼する：科目・単元・問題数・形式を選んで作成を実行すると順番待ちに入り、workerがOllamaにつながるときに順に生成してストックに入れる
- 作成依頼では、ほかに小単元・レベル・作成役と検証役のモデル・検証回数・解説の見直しをするかを依頼ごとに選べる（初期値は/statusの設定）
- 同じ順番待ちで、キーワード指定、子供からのリクエスト、間違えた問題の類題も処理する（後のフェーズ）
- workerはOllamaにつながらないときに落ちずに再試行する。/statusに生成の状態とストック残数を出し、残りが少ないときは画面にも表示する
- 検証：検証役には模範解答を見せずに解かせて突き合わせる。複数回解かせて一致したものだけ採用する。別系統のモデルにも解かせられるが、試した結果、正しい問題まで弾きすぎたので「使わない」を推奨する
- 検証役が解く前に、問題文・解説の表記を機械的に点検する（数学ならLaTeXの崩れなど。点検の中身は科目ごと）。落ちたら作成役に1回だけ直させる
- 検証役が全回一致した問題は、LLMに解説を見直させ、問題があれば不合格にする（依頼ごとに切れる）
- 解説・ヒントは生成時に作って保存する（後からLLMを呼ばない）
- 「この問題おかしい？」ボタン：押された問題は集計から外し、あとで開発者が確認する
- 問題検証モード（/review、親向け）：正解つきの一覧、削除、表記の点検で引っかかる問題の一覧、品質チェック用のMarkdownの書き出し（作った日・管理番号で絞れる）。書き出しをAIに点検させ、直しどころを集める

### 問題形式

| 形式 | 内容 | 採点（LLM不要） | 検証で確認すること |
| --- | --- | --- | --- |
| スマホ向け選択式 | 選択肢から選ぶ | 選んだ選択肢の一致 | 正解の選択肢が1つだけか、選択肢同士が重複しないか |
| キーボード入力 | 答えが一つに決まる数値・数式・英単語 | 数式はsympyで同値判定、英単語は完全一致 | 答えが一つに決まるか |

和訳や英作文のような記述式は扱わない。

### 数学

- 数値と答えをPython（sympy）で作り、LLMには問題文・解説・ヒントだけを書かせる（テンプレート方式）
- 誤答の選択肢は、符号ミスや公式の取り違えなど、よくある間違いをPythonで計算して作る
- 誤答がどれも正解と一致しないことをsympyで確認する

### 本文から作る科目（英語・公共）

「本文を用意 → 設問を作る → 本文だけで解けるか検証する」という共通の流れで作る。

- 英語：本文をLLMが書く
- 公共：Wikipediaや官公庁の資料を取得して本文にし、出典リンクを問題と一緒に表示する

## 科目

追加の順番：数学 → 英語 → 公共 → その他 → プログラミング（最後）

| 科目 | 出題の形 | 本文・答えの作り方 | 注意点 |
| --- | --- | --- | --- |
| 数学 | 選択式（キーボード入力の数値・数式も可） | Pythonで数値・答え・誤答を計算 | 誤答が正解と一致しないことを確認 |
| 英語（共通テストレベル） | 短めの英文＋2〜3問の読解、語彙問題。選択式が中心（キーボード入力ではスペル問題も可） | LLMが英文を書く | 英文だけで正解が1つに決まるか。リスニングは対象外 |
| 公共 | 選択式 | 資料を取得して本文にする | 法改正に合わせて新しい資料を使う。意見が分かれるテーマは制度や立場を問う形にし、正解を決めつけない |

- 英語：共通テストのリーディングには文法だけを問う問題がないため、読解と語彙を中心にする
- その他の候補：理科の計算（Pythonで確かめられる）、知識系（公共と同じく資料から作る）。国語は小型モデルが苦手なため後回し
- プログラミング：最後に追加。コードを書く問題はテストで採点し、模範解答がテストを全部通ることを確認してから出す

## 画面と入力

- 解き始め：科目と問題数（初期値20問）を選んで開始する。単元・小単元・レベルでも絞れる。間違えた問題の再出題を混ぜる。同じ小単元が続かないように並べる
- 開始時に端末（スマホ／キーボード）を選び、合う形式の問題だけを出す
- 選択肢はスマホで押しやすい大きさにし、1画面に問題と選択肢が収まるようにする
- 英語の読解は、英文と設問を同じ画面で行き来しやすくする
- キーボード入力の欄は、自動修正・候補表示・スペルチェック・先頭の大文字化をオフにする
- 過去問題の見返しと再挑戦ができる

## 記録と学習機能

回答の記録項目は最初から残す（集計画面は後のフェーズで作る）。

- 回答ごとに残す項目：日時、かかった時間、1回目か再挑戦か、ヒント・解説を見たか、科目・単元・問題形式・利用者
- 利用者：項目は最初から持たせ、切り替え画面（名前を選ぶだけ、パスワードなし）は後で作る
- 後のフェーズで作るもの：間隔をあけた再出題、単元ごとの「1回目の正解率」と「再挑戦後の正解率」、期間ごとの集計、テストモード（未出題の問題をヒントなし・時間制限ありで出し、単元ごとの点数を出す）、解説への検算コードの表示
- 集計は子供本人にも同じものが見えるようにする

## 信頼性と安全

- sandbox：ネットワークは `internal: true`（外部に出られない）、メモリ・CPUの上限と実行タイムアウト、root以外で実行、データのボリュームはマウントしない
- Pi 4は他のサービスと共用なので、全コンテナにメモリ上限を付ける
- workerは公共の資料取得のためにインターネットへ出るが、sandboxは出られないままにする
- 停電対策：HDDのマウント前にコンテナが起動しても、空のデータで動き出さないようにする（データの場所がHDD上にあるか確認し、なければ起動しない）
- データベースがSQLiteなら、書き込み途中の停電で壊れにくい設定にし、定期バックアップを取る
- ポート8000は家庭内のみで使い、ルーターでポート開放しない。既存コンテナとのポートの衝突を確認する

## 開発の進め方

- 開発者はgitに不慣れ。手順書のコマンドは省略しない
- フェーズごとに新しいセッションで進める。引き継ぎは `CLAUDE.md`（構成、守るルール、進み具合、次にやること）で行う
- 実装に入る前に計画と確認事項を出し、開発者の合意を得てから着手する
- フェーズの終わりに `CLAUDE.md` と README を更新する
- 科目ごとの詳細（その科目だけの作り方・点検・プロンプト・レビューの記録など）は、科目ごとのファイル（`docs/math.md`、`docs/english.md` など）に分けて書く。`CLAUDE.md` には科目によらない決めごとだけを書き、科目のファイルへリンクする。後でその科目を直すときは、そのファイルを見れば内容が分かるようにする

## 試運転版について

- Docker Desktop上で `ai-quiz` プロジェクトとして動いていた（web・worker・sandboxの3コンテナ）
- ほとんど使っていないため、データの移行は不要
- コードは流用できる部分だけ使ってよい
