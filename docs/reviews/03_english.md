## 2. Haiku と qwen の比較（英語）

| | Haiku（#495〜#503） | qwen（#484〜#493） |
|---|---|---|
| 本文の自然さ | 自然で一貫している | 論理の破綻が複数ある |
| 解説 | 根拠の選び方に軽微な難あり | 主客の逆転など内容の誤りあり |
| 誤答ラベル | 概ね正しい（1 件不一致） | 内容と合わないものが複数 |
| 修正が必要 | 6 問中 1 問（#495） | 6 問中 4 問 |

英語は本文の質が全体を左右するため、**本文は Haiku、設問はローカル**の分担を試したい（4 章の設定で実現する）。

## 3. 英語の生成・点検の改善

### A. 機械的な点検の追加（`check.py`）

1. **URL・メールアドレスは予約ドメインだけ許可**：`example.com` / `example.org` / `example.net`（とそのサブドメイン）以外の URL・メールが本文にあれば不合格 → #490
2. **語彙の意味の問題（`en-vocab-meaning`）の解説・ヒントに「空所」「入る」「入れる」がないか** → #497、#485
3. **ヒントに正解語の日本語の意味（`words.py` の意味欄）が含まれていないか**。今は英単語だけを見ている → #503
4. **読解のヒント・解説の人名**：本文に出てくる固有名詞（大文字で始まる語の連なり）が、ヒント・解説でカタカナ化されていないか。カタカナ化の検出が難しければ、プロンプト側のルール（B-3）だけでもよい → #495、#496

### B. 作成プロンプトの追加ルール（`prompts.py`）

1. 本文で性別が分からない人物（特に語り手）は、設問・選択肢で **the writer** と呼び、he / she を使わない → #493
2. 設問中の代名詞（his / her / their）は、指す人物が一意に決まるときだけ使う → #493 の「his hometown」
3. ヒント・解説の人名は英語表記のまま（例：Mr. Hale）。カタカナにしない
4. 架空の URL・メールは example.org などを使う
5. 語彙の意味の問題では「空所」という語を使わない（例文に空所はない）
6. 語彙の例文は、単独で読んで常識的に筋が通る内容にする → #485

### C. 根拠（Evidence）の扱い

- 気持ちの変化・比較・時系列を問う設問では、**根拠の文を複数（最大 2〜3 文）書けるようにする**。照合（`check.contains`）は各文について行う → #496

### D. 見直し（`review`）の観点を追加

今の観点（正解が 1 つに決まるか、英文の誤り、解説・ヒントの整合、日本語の自然さ）に加えて：

1. **正解の選択肢の各要素が、根拠の文で裏付けられているか**（本文にない要素が混ざっていないか） → #495
2. **誤答ラベルが、その誤答の内容と解説の説明に一致しているか**。一致しなければ見直し役に正しいラベルを選ばせて置き換える（`MISTAKES` の中から） → #501、#492、#490
3. **語彙の例文が常識的に筋が通っているか** → #485
4. 解説の主語・目的語が本文と一致しているか（誰が誰に何をしたか） → #492

### E. 本文単位の見直し（新規）

- 設問の検証の前に、**本文だけを 1 回見直す**：時系列、因果関係、矛盾、事実関係（「misunderstanding」の中身が誤解になっているか等）
- 「問題あり」なら本文ごと不合格（`en_passage_review` など。理由名は `en_` で始める）→ #491〜#493 の本文

### F. 語彙問題の難易度と誤答

1. **中学レベルの語を除外する**：`words.py` の高校基礎 577 語から、中学の学習語彙（中学の語彙リストと突き合わせ）を外す → #497 dream、#485 adult
2. **誤答の選び方を変える**：今は同じ品詞・レベルから無作為に 3 つ選んでいるため、意味が無関係で即答できる
   - 案：同じ品詞・レベルの候補を 10〜15 語渡し、作成役に「例文に入れても文法的には成り立つが、意味が合わない語」を 3 つ選ばせる
   - 正解が 1 つに決まるかは、今の検証（選択肢の並べ替え×複数回）と見直しで確認する
   - 意味が重なる語を除く今の仕組み（`pick_distractors` の 2 字の並び判定）は残す

### G. 読解の生成を 2 段階に分ける（4 章の前提）

今は作成役が 1 回の呼び出しで題名・本文・設問をすべて書いている。これを次の 2 段階にする。

1. **本文作成**：題材から題名と本文を書く（本文作成役のモデル）→ 本文の機械点検 → 本文単位の見直し（E）
2. **設問作成**：確定した本文を渡して設問を書く（作成役のモデル）→ 今の設問の点検・本文なしの確認・検証・見直し

- 本文は `passages` 表にストックし、**同じ本文に後から設問を足せる**ようにする（本文の使い回し）
- 本文なしの確認（`_blind_check`）は今どおり作成役のモデルで行う

## 4. 科目ごと・役割ごとの AI 設定

### 目的
科目によって向くモデルが違う（数学は qwen で十分、英語の本文は Haiku が明らかに良い）ため、**科目 × 役割**でモデルを設定・保存できるようにする。

### 設定の持ち方（案）

全体の既定値を持ち、科目ごとに必要な役割だけ上書きする。

```yaml
default:
  作成: qwen3.5:9b-q8_0
  検証: gemma4:e4b-it-qat
  見直し: gemma4:e4b-it-qat

数学:
  # 既定値のまま

英語:
  本文作成: anthropic/claude-haiku-5-5   # 英語だけの役割
  作成: qwen3.5:9b-q8_0                  # 設問
```

### 要件
1. 役割は **科目ごとに増やせる**作りにする（英語の「本文作成」、将来の公共で別の役割が要る可能性）
2. 設定は画面から変更・保存できる（既定値に戻す操作も）
3. **作成役と検証役が同じモデルなら警告**を出す（見落としが重なりやすいため）
4. **生成キューは科目ごとにまとめて処理**する。科目を交互に生成するとローカルモデルの入れ替えが増えるため
5. API モデル（Haiku など）を使う役割は、**科目ごとの 1 日の上限（回数または金額）とログ**を持つ
6. 各問題には今どおり作成役・検証役（＋本文作成役）のモデル名を記録する。科目×モデルのエラー率を後で比べられるように
7. 既存の設定（全体で 1 つ）からの移行：今の設定を `default` として引き継ぐ

## 5. 確認用のデータが欲しい

実装後、英語で次の 2 条件を **同じ小単元・同じ問題数**（例：各小単元 3〜4 問）で作り、まとめて書き出せるようにしてほしい。

1. 本文：Haiku、設問：qwen（検証：gemma）
2. 本文も設問も qwen（検証：gemma）

書き出しには、作成日時・作成役・本文作成役・検証役に加えて、**検証・見直しで不合格になった件数と理由**も含めたい（検証役の良し悪しを比べるため）。
