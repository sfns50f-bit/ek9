## 直すとよい点

### 1. 公共の資料が取れないと、ほかの科目の依頼も止まる

Wikipedia や e-Gov につながらない（混雑・403 を含む）と、公共の依頼は「待機」になり、60 秒ごとに同じ依頼からやり直します。worker は「直前と同じ科目」か「古い順」で次の依頼を選ぶので、後ろに並んだ数学・英語の依頼は、公共の依頼を取り消すまで進みません。

- 画面の表示も「Ollama を待っています」のままで、原因が資料だと分かりません。
- 直し方：待機にした依頼ごとに「次に試す時刻」を持たせ、その間はほかの依頼を先に進める。表示も「資料の取得を待っています」に分ける。
- 場所：`app/quizapp/worker.py:272`（`next_job_id`）と `app/quizapp/worker.py:907`。

### 2. API 側の順番待ちが、黙って止まることがある

API の順番待ちは別スレッドで動いています。依頼がないときの状態の書き込み（`app/quizapp/worker.py:967` 以降）は例外を受け止めていません。ここでデータベースの一時的なエラーが出ると、そのスレッドだけが終わります。

- プロセスは生きているので Docker は再起動せず、API の依頼は「順番待ち」のまま残ります。
- Ollama 側のメインのループで同じことが起きると、プロセスごと落ちて Docker が再起動するので、こちらは実害が小さいです。
- 直し方：ループ全体を try で囲む。数行で済みます。
- 起きる確率は低いですが、起きたときに気づきにくい種類です。

### 3. 科目を足すたびに中心部分に科目の事情が入っている

ルール 3（科目を足しても中心部分を触らない）は大筋で守られていますが、次の 3 か所は科目の中身を中心部分が知っています。

- `app/quizapp/stock.py:330` の `_STAGE`：「英文の点検」「本文なしの確認」など科目ごとの段階名を並べている。
- `app/quizapp/stock.py:358`：要確認が「事実」の判定だけで割れたかを、記録の文字列で見ている（公共だけの事情）。
- `app/quizapp/web.py:845` など：見本集の書き出しの科目の初期値が `"english"` 固定。

今は動きますが、フェーズ6で科目が増えると `stock.py` を毎回触ることになります。段階名の対応と「要確認の内訳」を `Subject` 側に持たせる形にしておくと、公共の見本集を作るときにも楽です。

### 4. 見返しの画面が、記録が増えると遅くなる

`/history`（`app/quizapp/web.py:335`）は、解いた問題すべてについて 1 問ずつデータベースを引き、そのあとで 300 件に絞っています。1 日 20 問なら 1 年で約 7,000 問、問い合わせは 1 回の表示で 1 万回を超えます。Pi では数秒かかるようになるはずです。

- 直し方：新しい順に 300 件だけを 1 回の問い合わせで取る。
- 今すぐ困る話ではないので、フェーズ5（集計）のときに一緒に直すのでも構いません。

### 5. CLAUDE.md が大きすぎる

CLAUDE.md は約 59KB あり、新しいセッションのたびに全部読み込まれます。半分ほどは「第 N 回のレビューで何を足したか」という経緯で、`docs/handover.md` や `docs/english.md` と重なっています。

- 困ること：毎回の読み込みが重い。今のルールと過去の経緯が混ざって、どれが現行の決まりか読み取りにくい。
- 直し方：CLAUDE.md は「構成・守るルール・今の決めごと・次にやること」だけにし、経緯と英語の詳細は handover と科目のファイルへ移す。特に「次にやること」の 2 番（英語の経緯）は 1 項目で 2KB を超えています。

### 6. 細かいもの

- 古い説明：`.env.example` の `OLLAMA_THINK` の説明が前の版のまま（「自動：qwen3 系は切る」）。`app/quizapp/config.py:38` の説明も同じ。今は「あり／なし」だけです。
- 公共の事実の判定のメモ（`app/quizapp/subjects/civics/__init__.py:400`）：検証を 1 回にすると、1 回目の結果が消されずメモリに残り続けます。量は小さいですが、worker の上限は 256MB なので、回数が 1 のときは残さないようにしておくと安心です。
- 管理の画面にパスワードがない：「作る」「状態 → モデルと思考モード」は誰でも開けるので、API の月の上限も画面から変えられます。家庭内 LAN なので実害は小さいですが、`REVIEW_PASSWORD` を設定しているなら同じパスワードをこの 2 画面にもかけられます。
- 自動テストが手元でしか走らない：GitHub 上でプルリクエストごとに `python -m pytest` を走らせる設定（GitHub Actions）がありません。テストは約 1 分で終わるので、足しておくと取り込む前に壊れていないか分かります。

## 問題なかった点

- API の料金表：`.env.example` と `docker-compose.yml` の 3 モデルの単価は、今の公式の料金と合っています。キャッシュの読み込みは Sonnet・Opus で実際より少し高めに見積もる側なので、上限を超える方向には働きません。
- 資料の取得先：2 つのホストだけに限定され、リダイレクトも追いません。
- 停電対策とバックアップ：目印ファイル、WAL、書き終えてからの名前の付け替えは、説明どおりに動く作りです。同じ HDD にしかない点は README に注意書きがあります。
- 子供の画面：LLM を呼ばないことはテストで確かめられています。画面に出す文章（LLM や Wikipedia 由来）はエスケープされています。

## おすすめの順番

公共の実機確認を続ける前に 1 と 2 を直すのがよいと思います。どちらも小さな変更で、公共は資料の取得が絡む分、1 に当たりやすいからです。3 は公共の見本集を作るとき、4 はフェーズ5、5 はフェーズ3を締めるときの CLAUDE.md の更新（ルール 11）に合わせるのが自然です。

## 対応（2026-11-10）

- **1**：資料の取得先につながらないときは、科目が `base.WaitForSource` を投げ、worker はその依頼だけに「次に試す時刻」（`Worker.job_retry_at`）を付けて、その間はほかの依頼を先に進める（`next_job_id`）。Ollama の待ち（`unavailable_until`）にはしない。依頼の説明は「資料の取得を待っています：…（ほかの依頼は先に進めます）」、worker の状態も「資料の取得を待っています」。依頼の状態の名前は「Ollama を待っています」から「待機中（つながるのを待っています）」に（何を待っているかは依頼の説明に出る）
- **1 の直しの不具合**（#31 を Fable が確かめて見つけた）：資料を待つたびに作り直しの回数（`gen_attempts`）が減り、問題を 1 つも作らないうちに依頼が「失敗」になっていた（1 問の依頼なら約 3 分）。`WaitForSource` のときも Ollama の待ちと同じく数え戻すようにし、5 回続けて待っても回数が増えず失敗にならないことをテストで確かめる
- **2**：依頼がないときの状態の書き込みを `_idle_status` に分け、例外を受け止めてループを続ける
- **6 の 1・2 つめ**：`OLLAMA_THINK` の説明を今の「あり／なし」に直した。公共の事実の判定のメモは、検証が 1 回のときは残さない（worker が `options["_runs"]` で回数を渡す）・500 件で古いものから捨てる
- **3・4・5、6 の 3・4 つめ**：おすすめの順番どおり後で行う（3 は公共の見本集を作るとき、4 はフェーズ5、5 はフェーズ3を締めるとき）。管理の画面のパスワードは**かけない**（API は自動の追加課金をしていないので上限までしか使われない。問題検証モードのパスワードも、本人の勉強用なので実際には入れない予定）。GitHub Actions は**今は入れない**（今のところ不具合がなく、プッシュの前に手元で `python -m pytest` を流している。利点は、開発者が画面で合否を確かめられることと、本番と同じ Python 3.12 で確かめられること。トークンの節約にはならない）。どちらも 2026-11-11 に開発者が決めた
