# 公共の作り方の詳細（フェーズ3）

公共の問題を直すときは、このファイルだけを見れば分かるようにする（CLAUDE.md のルール 13）。科目によらない決めごとは [CLAUDE.md](../CLAUDE.md)。

コード：`app/quizapp/subjects/civics/`

| ファイル | 役割 |
|---|---|
| `catalog.py` | 単元・小単元（`UNITS`・`SPECS`）、資料の一覧（`SOURCES`）、誤答の種類（`MISTAKES`）、本文 1 つの設問の数（`questions_for`）。web も読む |
| `sources.py` | 資料の取得（e-Gov 法令 API・Wikipedia）と抜き出し、鮮度の調査（`check`）。**worker だけが読む**（`generate` と `check_source` の中で読み込む） |
| `check.py` | 設問の機械的な点検（根拠の文が資料にそのまま入っているか・選択肢の重複・否定形の設問・意見を問う設問・記号で呼ぶ解説など）、検証役の引用の照合（`near_quote`）。sympy なし |
| `prompts.py` | 設問の作成・解説の書き直し・選択肢ごとの判定・事実としての判定・見直しのプロンプト |
| `__init__.py` | `CivicsSubject`（作成・検証・見直し・鮮度の調査・問題検証モードの点検） |

選択肢ごとの判定の読み取り・引用の取り出し・見直しの読み取りは、英語と共通の部品（`subjects/choicejudge.py`）を使う（フェーズ3で英語から切り出した。英語の動きは変えていない）。

## 0. 開発者と決めたこと（2026-11-04）

- 依頼文はない。仕様書（docs/spec.md）の「公共」と「本文から作る科目」に沿って作る
- **資料は Wikipedia 日本語版と e-Gov の法令だけ**から取る（官公庁のページは、ページごとに作りが違って読み取りが壊れやすいので後回し）
- **資料は書き換えずにそのまま本文にする**（LLM に書き直させない。正解の根拠の文が本文にそのまま入っているかを機械で確かめるため）。長いものは段落・文の切れ目で切る（`clip`、1300 字まで。切ったら法令は「（以下略）」、画面に「一部を抜粋」）
- 英語の判定の部品は共通の部品に切り出す（`subjects/choicejudge.py`）
- 単元は下の 1 章のとおり（使用者本人に確認済み）
- **資料の鮮度**：一定の日数で捨てるのではなく、**定期的に鮮度を調べる仕組み**を入れる（3 章）。変わった資料の問題を「残す」か「古い問題の印を付ける」かは、まだ決めていない（今は消さずに残し、問題検証モードで一覧できるだけ。4 章）

## 2. 作成と検証の流れ

（第 14 回のレビューで変えたところは 7 章：選択肢ごとの理由、根拠の差し替え、見直しでの作り直し、事実の判定の 2 回一致など）

| 段階 | 中身 |
|---|---|
| 資料 | 小単元の資料の一覧から、まだ使っていないもの（資料が変わったものも）を選んで取ってくる（`sources.fetch`）。つながらない・混んでいる（403・429・5xx・Wikimedia の「too many requests」）ときは `LLMUnavailable` で依頼を「待機中」にする（作り直しの回数を使わない）。設問が足りない資料（前に取った資料のうち、出典が変わっていない・見つかるもの）には設問を足す（`reuse_passages`） |
| 作成 | 作成役が設問を書く（`prompts.QUESTION_SYSTEM`）。欄は英語の読解と同じ `Question / A〜D / Answer / Wrong / Evidence / Hint / Explanation` |
| 点検 | `check.question_issues`：根拠の文が資料にそのまま入っているか（空白・全角半角・かぎかっこは無視）、選択肢 4 つ・重複なし・日本語、誤答の種類、「誤っているもの・適当でないもの」を選ばせる設問でないか、意見・賛否を問う設問でないか、ヒントに正解が書かれていないか、解説・ヒントが選択肢を記号で呼んでいないか、中国語の字・内部の言葉。落ちたら 1 回だけ直させる。解説が空・短いだけなら解説だけを書き直させる |
| 検証（e4b ×2。思考あり） | 選択肢ごとの判定（`prompts.CHOICE_VERIFY_SYSTEM`。資料の引用つき。「裏付けあり」「一部だけ合う」の引用は資料と照らし、資料にない引用はやり直させる）→ 正解だけが裏付けありなら合格。**事実としての判定**（`prompts.FACT_SYSTEM`。資料を見せず知識で）：誤答が「正しい」なら「事実として正しい誤答」、正解が「誤り」なら「正解が事実と食い違う疑い」で、どちらも**要確認**（不合格にはしない。小さいモデルの知識の判定は揺れるため）。読めなければ記録に残すだけ |
| 見直し（12b） | 解説・ヒントが資料と合っているか（条文の主体・条件・数）、古い制度を今のもののように書いていないか、意見が分かれるテーマで立場を決めつけていないか（`prompts.REVIEW_SYSTEM`） |
| 合否 | 2 回とも合格でストックへ。割れたら要確認（英語と同じ `verify_split_check`） |

- 公共には「本文なしの確認」（英語の、本文を読まなくても解ける設問を外す確認）はない。公共は知識として覚えている生徒が解けてよい科目で、資料は正解を確かめる根拠のために付けている
- 誤答の種類（`MISTAKES`）：資料と食い違う／資料に書かれていない（事実としても誤り）／一部だけ合っている／主体・時期・数などの取り違え
- 検証のやり方の切り替え（`verify_options`）：`fact_check`（事実としての判定。既定は「する」）、`reuse_passages`（資料の使い回し。既定は「使う」）
- 既定のモデルは英語と同じ形から始めた（作成 26b・検証 e4b ×2 思考あり・見直し 12b）。見本集（`docs/reviews/golden_set_civics.json`）を作ってから見直す

## 3. 出典の表示と鮮度の調査

- 本文の表（`passages`）に、出典の名前（`source_title`）・URL（`source_url`）と、取ってきた資料の記録 `source_info`（フェーズ3で足した列）：`kind`（law / wiki）・`key`・`parts`（条）・`section`・`revision`（法令は `law_revision_id`、Wikipedia は `revid`）・`fetched_at`・`clipped`・`license`・`license_url`
- 出典の URL：法令は `https://laws.e-gov.go.jp/law/<法令ID>`、Wikipedia は取った版への固定のリンク（`index.php?title=…&oldid=<版>`。CC BY-SA 4.0 の表示に、どの版を使ったかを示すため）
- 解く画面・答えた後・問題の画面の本文の下に「出典：〈リンク〉（取得した日・一部を抜粋）。ライセンス：CC BY-SA 4.0」（`_macros.html` の `passage_source`。出典の URL がない本文＝英語には出さない）
- **鮮度の調査**（`Worker.maybe_check_sources` → `Subject.check_source` → `sources.check`）：
  - Ollama 側の順番待ちの合間に 1 時間ごとに見に行き、`SOURCE_CHECK_DAYS`（既定 30 日。0 は調べない）より前に調べた（まだ調べていない）資料を、古いものから 20 件まで照らし直す
  - 法令：今の版の番号（`/laws?law_id=`）が同じなら「変わっていない」。違えば条文を取り直し、使った条文が同じなら「変わっていない（ほかの条の改正）」、違えば「資料が変わった」
  - Wikipedia：版の番号が同じなら「変わっていない」。違えば記事を取り直し、使った部分（行ごと）が今の記事にそのまま残っていれば「変わっていない」、なければ「資料が変わった」
  - 記事・法令がなくなったら「資料が見つからない」
  - 結果は `source_info` の `check`・`checked_at`・`detail`・`current_revision`、初めて変わったと分かった日 `changed_at`。まとめは kv の `source_check`（「状態」のまとめに出る）
  - 断られた（404・403・429 以外の 4xx）・応答が読めないときは「調べられない」で、前の結果を残して次の回にまた調べる（`source_info.last_error` に理由。問題検証モードに出る）。403・429・5xx・つながらないときはその回の調査をやめる
  - 変わった・見つからない資料には新しい設問を足さない。問題は消さない
  - **資料が変わったら、同じ資料の新しい版を取ってきて作れる**（「法改正に合わせて新しい資料を使う」。仕様書）。同じ問題の印（`params_key`）に資料の版を含めるので、古い版の問題と重複にならない。古い版の問題はそのまま残る（扱いは 4 章）
  - 「状態」のまとめの「いま資料が変わった・見つからない」の数は、毎回すべての本文から数え直す（知らせが次の回で消えないように）
- 日付（取得した日・調べた日・変わったと分かった日）は日本時間で出す（`isodate`）
- 問題検証モードの状態「ストックと要確認のうち出典の資料が変わった・見つからない問題」（要確認を通す前に気づけるように）で一覧でき、各問題に鮮度の調査の結果が出る。Markdown の書き出しにも出典と鮮度の調査の結果が出る
- 取ってきた資料は「表記をまとめて直す」でも書き換えない（資料のとおりに見せ、鮮度の調査で照らすため）

| ヒントが正解の語句を指す（#1401「ナチズムの台頭と…」） | プロンプトで禁じ、点検（`check.answer_terms_in_hint`）で、正解の選択肢にだけある語句（漢字・カタカナ 3 字以上）がヒントにあれば直させる |

## 7. 第 14 回のレビュー（[docs/reviews/14_civics.md](reviews/14_civics.md)）への対応（2026-11-10）

合格した 23 問のうち手直しなしで使えるのは約 15 問、合格率 20%（114 問中 23 問）。仕組み側で減らせる原因（表の取り込み・事実の判定の誤検出・解説だけ悪い問題を捨てていた）を中心に直した。

| 章 | 指摘 | 対応 |
|---|---|---|
| A-1 | 表の見出しが落ちて主語のない文ができる（社会保険・直接請求。#1479 の取り違え） | Wikipedia は**記事の HTML（`action=parse`）を受け取り、自前で文章にする**（`sources.html_to_text`）。表・情報の箱・脚注の印・注記・画像・目次は入れない（表は飛ばす）。小見出し（h3 以下）と定義の語（dt）は「【見出し】」の行で残し、続けて入れる節にも「【節の名前】」を付ける。前の版（本文だけの API）で取った本文は、鮮度の調査では記号を除いて照らす（表のセルが入っていた本文は「変わった」になり、点検の対象に出る） |
| A-2 | 主語のない短い文の警告 | 表を入れなくなったので見送り（実機の結果で、まだ残るなら足す） |

## 8. 第 16 回のレビュー（[reviews/16_civics.md](reviews/16_civics.md)）への対応

合格率 37%。合格 57 問のうち 5 問は正解が誤り・正解が 1 つに決まらなかった。直したのは科目の中（`subjects/civics/`）だけで、中心部分（worker / web / stock / db）は触っていない。

| 指摘 | 内容 | 対応 |
|---|---|---|
| A-1 | 論争的・出典の弱い段落を根拠にしている | 資料の一覧から Wikipedia「非正規雇用」を外し、労働契約法 3・16・17 条を足した。設問の点検に「根拠の文が意見・推測・批判の文（と思われる・と批判され・問題視され・疑念 など。`check._HEDGE_RE`）なら直させる」を足した。作成の指示にも書いた。「政党交付金」「介護保険」「市場の失敗」の記事は残している（節・段落の指定はしていない） |
| A-2 | 見出し・箇条書きの欠け | `sources.tidy`：長くて切ったときの途中の箇条書きを丸ごと落とす、「以下の〜を定義している。」のように箇条書きが続くはずなのに続かない段落を落とす、それで空になった見出しを落とす（文章は書き換えない。鮮度の調査は行ごとに照らすので影響しない）。`drop_trailing_headings` は箇条書きの行（「・」）を落とさない（マズローの 5 段階が 3 つで切れていた原因）。「直接請求」の見出しの欠けは、前の版の取り込み（11/06。本文だけの API）で取った本文の使い回しが原因 → 下の A-3 |
| A-3 | 外した資料・前の版の本文の使い回し | 設問を足す本文から、資料の一覧にない資料（エリクソンの経歴など）と、前の版の取り込みで取った Wikipedia の本文（`source_info.format` が `html` でない）を外した（`_old_extract`）。前の版の本文の資料は「使った」に数えたままなので、取り直したいときは本文を削除する。作成役に渡す「すでにある設問」に「同じ内容を正解にしない」を足した |
| B | 資料どおりに正しい文を誤答にする（不合格の 24%） | **誤答だけの差し替え**（`_swap_wrong`）：検証の 1 回目で、正解は裏付けられていて、誤答が「資料で裏付けられる」「事実として正しい」とされたことだけで止まったら、その誤答だけを作成役に作り直させ（検証役の指摘を渡す。設問・正解・ほかの選択肢は変えない）、機械的な点検のあと同じ回の判定をかけ直す。通れば差し替えた形で 2 回目の検証・見直しに進み（`_swap_memo`）、合格したときだけ選択肢と解説を書き込む（`VerifyResult.updates`）。差し替えても止まれば差し替えずに前の判定のまま。検証のやり方 `swap_wrong`（する／しない。既定はする）。作成の途中の問題だけ（検証のテスト・見本集の測定・見直しのやり直しではしない）。作成の指示にも、誤答の作り方（資料の特定の語を逆か別の値に変える。言い換え・限定の語の出し入れ・2 つの文をつないだだけは誤答にならない）と、理由を「書かれていない」「限らない」だけで終わらせないことを足した |

| D-1 | 見直し役の弾きすぎ | 理由・ヒントを作り直した後の 2 度目の「問題あり」は、不合格（`cv_review`）ではなく**要確認**（`needs_check`。問題検証モードで確かめて通す・捨てる）。作り直せなかったときは今までどおり不合格 |
| D-2・D-3 | 補足知識を誤りとする・別の選択肢の文を引いた理由の見逃し（#1526） | 見直しの指示に「資料にない知識での補足は誤りではない」「誤答の理由がその選択肢自身の文を扱っているか」「指摘の前に資料で確かめる」。設問の点検でも、理由が別の選択肢の文をそのまま引いていたら理由を書き直させる |
| E | 書き出し（不合格の一覧が 30 件まで・作成 0 の依頼の理由・不合格の問題の選択肢） | 未対応（中心部分の `stock` / `review` の変更になる） |

- 合格した 57 問・要確認の扱い（レビューの 1 章）は開発者が問題検証モードで行う
- 差し替えは、検証の途中で作成役のモデルを呼ぶので、ローカルではモデルの入れ替えが増える（見直しの作り直しと同じ）。遅すぎれば `swap_wrong` を「しない」にする
- 実機の結果（第 17 回。[reviews/17_civics.md](reviews/17_civics.md)）：合格率 37% → 58%。差し替えは合格 32 問のうち 7 問で働き、差し替える前の誤答は 7 問とも資料どおりに正しい文だった。差し替えた後の誤答は 5 問が良く、2 問は甘い。合格した問題のうち正解が誤り・1 つに決まらないものは 3 問（9%）で変わらず、どれも資料の外の知識が要る型（次は C の「知識だけの事実の判定」）
- 第 17 回と一緒に直したこと：資料にある言葉（「与えられた」など）を引いた理由・ヒントを内部の言葉として弾かない、差し替えができなかった理由を検証の記録の 1 行目に残す、本文の途中の「【出典】」「【脚注】」などの小見出しとその中身を落とす
